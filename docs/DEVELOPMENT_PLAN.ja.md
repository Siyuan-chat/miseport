# MisePort 開発計画 — 2026年10月29日版

> **状態:** 計画（PLAN_ONLY）。工程・期限は目標であり、ユーザー向け機能の実装・本番公開・第三者の承認を意味しません。
>
> **主目的:** 日本の小規模EC事業者が、**自分のショップを許可の範囲でMisePortに接続し、商品を自動読込 → 確認 → Agent向けデータを生成・公開できる**。オープンソース・軽量・無料優先・商店所有を維持する。
>
> **現在の基線:** [PROJECT_STATUS.md](../PROJECT_STATUS.md)／[ADR-0001](PRODUCT_STRATEGY.ja.md)／[ADR-0002](CONNECTOR_ARCHITECTURE.ja.md)。この文書の「今後の予定」と、実際に検証された機能は必ず分ける。

## 0. 仕様を固定する範囲

- **初期の中心は「商店ごとの自主管理ツール」**。中央商品マーケットプレイス、価格比較サイト、決済・注文処理、大規模なマルチテナントSaaSを作らない。
- **商品取得の主導線は公式API**。商店主が自分のOAuth認可・読み取り専用PATなどを設定する。自分の認可済みAgent経由も任意。CSV/JSONは**常設の代替経路**。
- **商品情報の正確さを優先**。SKU／バリエーション、公開・非公開、価格、税、送料、在庫、商品URL、出典、更新日時を検証し、不明値は不明のまま保持する。
- **実店舗の秘密情報をMisePortの公開デモに送らない**。API資格情報をブラウザ公開コード、公開ZIP、ログ、Issue、動画に含めない。
- **CLI/MCPを残したまま、商店向け日本語UIを主製品へ**。商店はPython・Git・Docker・コマンド操作不要を目指す。
- **外部プロトコルと形式はAdapterで扱う**。現在の `miseport/1.1` 契約をベースに、Schema変更が必要な場合はバージョンを上げる。MCP、REST、JSON-LD、公式ECの入力CSVと出力CSVは異なる契約として検証する。
- **利用料の位置づけ**。MisePortのコードはApache-2.0、ローカル利用は原則無料。ただしショップの有料APIプラン、クラウドの無料枠超過、ドメイン購入などの外部費用は別途発生し得る。

## 1. 技術設計（実装前にスパイクで最終決定）

既存のPython決定論的CoreとSchema/契約テストを維持し、以下を追加する。**認証方式が異なるため全プラットフォーム共通の「APIキー入力欄」を設けない**。

| 層 | 構成案 | 責務 |
| --- | --- | --- |
| Merchant UI | 小型の日本語Web UI（Preact/TypeScript等、依存最小化） | ショップ選択、接続テスト、公開商品選択、監査、エクスポート、更新、エラー説明 |
| Browser-only fallback | 静的サイト側でCSV/JSONをクライアント内解析 | アカウント・資格情報不要のファイル検証とエクスポート。外部APIへ直接アクセスしない |
| Local Connector Companion（候補） | Pythonの既存Coreを利用した商店PC上の小型ループバックプロセス。将来はWindows/macOS向けダブルクリック起動パッケージ | 公式API呼出、認可状態、トークン保管、商品同期。開発者用CLIとは別にノーコード入口を提供 |
| SourceAdapter | BASEを最初に実装、その後プラットフォーム別プラグイン | API取得、ページネーション、商品／種類の識別、公開状態、更新時刻、失敗・リトライ |
| Canonical Core | 現行Pythonモデル・検証・監査・JSON-LD | SourceRecordからバージョン付きCatalogへの決定論的変換、根拠・不明値の保存 |
| Export/Publish | JSON/CSV/JSON-LD、商店別の静的配信用ZIP、任意の読み取り専用REST/MCP | 商店が所有する配布先で公開。MisePort中央への商品集約は行わない |

### Local Companionの採用判断（G1ゲート）

公開のMisePortページにPATを貼らせる方式は採らない。ブラウザだけで完結する公式API接続が可能かどうかは、各APIのCORS・OAuth・シークレット要件で決まる。**第一候補は商店PCで動くローカル補助アプリが接続し、同じローカルoriginで日本語UIを表示する構成**。先に動作・サイズ・セキュリティを実測してから採用を確定する。ユーザー体験上はダブルクリック起動を目指す。

- ループバック `127.0.0.1` のみで待ち受ける。Host/Origin/CSRF/ローカル要求認証を検証し、管理APIをLANや公共インターネットへ露出しない。
- Windows Credential Manager／macOS Keychain等、可能なOSの秘密情報ストアを利用し、**暗号化されないローカルファイルへの自動フォールバックは禁止**。サポート環境の差は手順書で明示。
- 長期TokenをURL、ローカルブラウザ保存、静的バンドルへ配置しない。トークン削除・失効・API接続解除を独立して実行可能にする。
- CLIは既存の開発者用として継続。ディスク容量・起動時間・メモリ使用・配布バイナリのサイズを計測し、重すぎる場合は方式を再評価する。
- 常時同期が必要なら**商店所有の任意ランナー**が必要。PCを閉じた状態で無料かつ無人の継続同期を保証しない。

## 3. プラットフォーム対応順序

対応項目を**公式API取得 / 公式CSV読込 / 公式CSV書出 / ショップへの書戻し**に分けて管理する。初期のショップへの書戻しは**対象外**。

| プラットフォーム | 初期の優先タスク | 外部依存・注意 |
| --- | --- | --- |
| **BASE** | **最初のネイティブ読み取りAPI**：v2 β PAT・items.read、商品一覧と種類の取得。公式CSVプロファイルも整備 | β仕様変更、PAT有効期限、現段階でOAuth未提供 |
| **Shopify** | 商品CSV読込／検証。ネイティブAPIは公式アプリ認証を使う第二候補 | App installation / approved read_products、必要に応じread_inventory。静的サイトにAPI secretを埋め込まない |
| **makeshop** | 商品CSV読込／書出形式を調査。ネイティブGraphQLは登録・認証できる場合 | 自社利用／ベンダーアプリの申請・料金・Webhook等が異なる。無条件無料とは宣伝しない |
| **カラーミーショップ** | CSVプロファイル、認可済みAPI/既存CLIとの連携可能性を検証 | OAuthおよび現行API仕様・必要な利用条件 |
| **EC-CUBE** | CSVプロファイル、各バージョンのWeb APIプラグイン導入条件を調べる | バージョン、プラグイン、商店管理者の作業が必要 |
| **STORES / 楽天 / Yahoo!** | 公式情報とCSV経路を調査、協力店舗があれば段階追加 | STORES APIはパートナー登録が必要、フリープラン不可。大規模プラットフォームごとに条件が異なる |

出典：[BASE API β](https://apiv2.thebase.com/docs/) / [商品API](https://apiv2.thebase.com/docs/reference/) / [Shopify認証](https://shopify.dev/docs/apps/build/authentication-authorization) / [makeshop Apps](https://developers.makeshop.jp/) / [EC-CUBE Web API](https://doc4.ec-cube.net/eccube-api4) / [STORES API](https://faq.stores.jp/hc/ja/articles/28207143147545--API%E9%80%A3%E6%90%BA-%E9%96%8B%E7%99%BA%E8%80%85%E5%90%91%E3%81%91API%E9%80%A3%E6%90%BA%E6%A9%9F%E8%83%BD%E3%81%A8%E3%81%AF%E4%BD%95%E3%81%A7%E3%81%99%E3%81%8B)。

## 7. 失敗時の代替経路・外部依存

- BASE β APIが更新・制限された場合、Adapterをバージョン固定し、API実店舗Pilotを遅らせて**公式CSV fallback**から商店UIを検証する。API優先の長期方針自体は変更しない。
- Shopifyやmakeshopのアプリ審査・API料金が導入障壁なら、他の対応可能なショップ・プラットフォームで実証する。無許可アクセスや規約回避はしない。
- 非技術者がLocal Companionを難しいと評価したら、インストーラー・初回UI・エラーメッセージを改善する。認証トークンを公開Webに置く「簡単な抜け道」は採らない。
- 一時的な無料ホストでも外部利用規約・利用枠・将来の価格変更がある。Cloudflare Pagesの[Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/)はZIP手動アップロードを提供するが、Webへの公開と、既存ショップへのJSON-LD埋込みは別作業。
- 無料の公開MCPを置いただけでMuse等から自動選択・公式登録されるとは限らない。アカウント内の実測、他ユーザーからのアクセス、公式投稿・審査・掲載は状態を分ける。

## 8. 実行・レビューの進め方

1. **各ゲートは原則「仕様→実装→自動テスト→非技術者の実測→日本語手順・実画面動画→Release」**。機能やドキュメントの更新はPRか追跡可能なcommitで行う。
2. 公開コード・回帰試験・サンプルデータ・英日ドキュメントはGitHubに残し、商店の秘密情報は残さない。デモは架空データだけ。
3. 期限が迫ってもP0の実行可能性、安全性と品質を優先し、未完了ならRelease注記へ明示する。**G0とG2を混同しない**。
4. 実際の週間作業量は未確認。表の日付は仮の計画で、1名開発＋AI支援を前提とする。権限・実ショップ提供・OSテスト・連休・審査の遅れは日程変更要因として扱う。
5. ドメイン購入、商店への連絡、第三者コミュニティへの投稿、公開Connector審査への正式提出、ショップ管理画面への接続は、必要な所有者権限と確認を得てから実施する。

---

**この計画が完成した状態の判定:** *普通の日本の店主が、MisePortの日本語画面と手順書だけで、自分のショップの正式な読み取り権限を設定し、公開商品を確認して、必要な形式でダウンロード／自分の公開先へ配信できる*。その後も商品と認証情報は店主自身の管理下にあり、MisePortの中央マーケットプレイスへの登録は必要ない。
